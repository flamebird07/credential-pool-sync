# v7.1.0 审查发现与修复记录

## 背景

2026-07-29 用户报告 Hermes session reset 显示 `doubao-seed-2-1-pro-260628`（已 429），但实际通过 fallback 在用 `glm-5-2-260617`。用户明确指出"不需要切换，是显示错误"。由此引发对凭证池代码的全面审查。

## 审查发现的问题

### 1. subprocess.run 缺编码参数（P1）

- **位置**：`sync_credential_pool.py`（cleanup_fallback_chain 中 2 处）、`switch_next.py`（run_sync 1 处）、`auto_bootstrap.py`（run_sync 1 处）
- **问题**：`subprocess.run(..., text=True)` 未指定 `encoding` 和 `errors`，Windows 默认编码（cp1252/gbk）解析中文输出时 `UnicodeDecodeError`
- **修复**：所有 `subprocess.run` 调用加 `encoding="utf-8", errors="replace"`
- **历史**：108 机器之前已修复但 87 源未同步，本次彻底统一

### 2. 脚本版本号不一致（P2）

- **问题**：`sync_credential_pool.py` docstring 仍写 "v2.0"，SKILL.md 已升到 v7.0.0
- **修复**：统一为 v7.0.0

### 3. cron_sync.sh 脆弱搜索（P2）

- **问题**：用 `find /c /d /e /f "$HOME" -maxdepth 5 -name sync_credential_pool.py -path "*/credential-pool-sync/*"` 跨盘搜索，慢且不可靠
- **修复**：直接用 `$HOME/AppData/Local/hermes/skills/devops/credential-pool-sync` 已知路径

### 4. auto_bootstrap.py 不回写飞书状态（P1）

- **问题**：`auto_bootstrap.py` 切换成功后只更新 config.yaml，不更新飞书"使用中"标记，`switch_next.py` 有此逻辑但 `auto_bootstrap` 缺失
- **修复**：在 `write_runtime_config` 成功后添加飞书状态回写：标记新凭证为"使用中"

### 5. auto_bootstrap.py 超时过短（P2）

- **问题**：`run_sync()` 超时仅 20s，网络稍慢即超时
- **修复**：20s → 60s

### 6. fallback_providers 含已失效模型（P2）

- **问题**：`doubao-seed-2-1-pro-260628` 已 429（SetLimitExceeded），仍在 fallback_providers 列表中
- **修复**：从 config.yaml 移除

## 关键教训

"显示错误的模型"不等于"需要切换凭证"。Hermes fallback 机制可能已经自动切换了 config.yaml 中的主模型，session banner 显示的是旧缓存。必须先读 config.yaml 确认实际状态，再决定是否需要操作。
